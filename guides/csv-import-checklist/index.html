The useful last pass

A practical CSV import checklist.

A file can open in a spreadsheet and still fail a destination import—or change more than you intended. Use this checklist to inspect structure, content and update risk before you hand it over.

For recurring exports and supplier filesIndependent guideUpdated November 2026

1. Keep the original and check the destination format

Save an untouched source copy first. Then look at the destination's current import template or documentation, not just last month's file. Confirm whether it expects a header row, exact header spellings, comma or tab separators, a specific date format, and an update key such as an ID, email or SKU.

“CSV” is a family of plain-text formats. Different programs may use tabs or semicolons, and spreadsheet software can reinterpret values when you open or save a file.

2. Confirm the shape before checking individual values

  • Does the first row contain the expected column names?
  • Are any headers blank or repeated after trimming spaces?
  • Does each record have the same number of fields as the header?
  • Are there fully empty rows at the beginning, middle or end?
  • Do quoted descriptions contain commas, line breaks or quote characters that need proper escaping?
  • Does the delimiter match what the destination expects?

A row with one extra delimiter can shift several values into the wrong columns while remaining visible as a single line in a spreadsheet.

3. Check the values that spreadsheet previews can hide

Apply rules that match the actual destination: which columns must be present, whether an identifier should be unique, whether numeric values can be negative, and what date or status values are allowed. Do not make a field “required” just because a generic checklist says it often is; use the receiving system's current rules.

  • Look for missing IDs, SKUs, names or email addresses where your workflow requires them.
  • Check duplicate keys separately from identical duplicate rows. A duplicate identifier may update the same record twice.
  • Review empty cells in columns that are being updated. Blank-value behavior differs across platforms and import options.
  • Look for number and date values changed by spreadsheet auto-formatting, especially leading zeros, large IDs, decimal separators and dates.
  • Trim accidental spaces only after checking that spaces are not meaningful in that field.
  • Inspect accented and non-Latin text for encoding damage.

4. If this is an update, compare it with a trusted version

A file can be structurally valid but still contain unexpected changes. If you have an earlier export, compare the baseline and new file using a key column. Review records that are new, absent, duplicated or changed—especially price, stock, account status and other high-impact fields.

RowReady's comparison mode reports record and cell differences in your browser. It does not merge files, decide what is safe, or write changes back to your application. A report can contain changed values, so store it carefully.

5. Check platform-specific dependencies

Some formats have fields that depend on other fields. For example, Shopify's product CSV guidance documents a variant update risk involving the Option1 name and Option1 value columns. A missing column may matter even when a generic structural checker sees consistent rows. Read the Shopify product CSV safety guide if you are preparing that kind of update.

6. Review the destination's own import preview

Use a small test where the platform allows it, look at the receiving system's preview and warnings, and keep a rollback plan. A third-party checker cannot see your custom fields, current records, permissions, configuration or import choices. A green result is a helpful signal—not a guarantee.

Frequently asked questions

Can I validate a CSV without uploading it to a website?

Yes. A browser tool can read a file selected on your device and perform checks locally. RowReady is designed this way; this does not mean every online file tool works the same way.

Does a valid CSV always import correctly?

No. The file can be syntactically valid while missing platform-specific fields, containing values rejected by account settings or asking an update to change records unexpectedly.

Should I delete duplicate rows automatically?

Not without reviewing them. Two identical rows may be accidental, but in some data workflows repeated rows can have meaning. Keep the source file and decide before removing anything.
